Astryx：昨天才講過，今天又來——連莊不是偶然，是敘事還在發酵

meta / astryx · MIT 協議 · TypeScript · 目前 Beta · 基於 React 19+ 與 StyleX

插畫：同一套積木、同一份說明書——真人蓋的頁面跟 AI 蓋的頁面長得一模一樣，這就是 Astryx 賣的「人跟 AI 共用同一套工具」。

一句話人話

昨天那期才講過它，今天它又拿第一——Meta 的設計系統連莊了，總星兩天從 19,950 衝到 22,718。昨天講的是「它是什麼」，今天要講的是「為什麼還在漲」。

它到底是幹嘛的

一個開源設計系統，目前還在 Beta，在 Meta 內部長了八年，撐著公司裡 13,000 多個應用。150+ 個無障礙元件、七套現成主題、深色模式、現成模板，外加一個 CLI 管家。裝法：npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex，再加 npm i -g @astryxdesign/cli，需要 React 19 以上。昨天已講過的四個賣點——內部開放、樣式不綁死、主題就是一組 CSS 變數、人跟 AI 共用同一套工具——今天不重複，詳見上一期。

它火在哪

一是連漲第三天：11 月 8 日 +863 星（增幅 5.47%，在舊的 10% 門檻下沒進主榜）、11 月 9 日 +3,324 星（19.99%）、今天 +3,111 星（15.87%）——熱度不是一日遊，是放量之後站穩了。二是絕對新增也是全場第一：今天全場沒有任何專案一天新增超過它。三是敘事踩得正：從 agent-desktop、auto-ontology 到 Astryx，這一波漲得兇的專案都在回答同一個問題——AI 越來越會寫東西，流程要怎麼跟上。Astryx 的答案是把設計系統做成「人跟 AI 的共同語言」，這個故事現在很有市場。

值得學什麼

昨天講了主題變數化、swizzle、文件＋API＋CLI 三件套，今天補一個更值得偷的點：「agent-ready」不是貼標籤，是真的把 CLI 當成產品來做。README 裡 CLI 有自己的篇幅——astryx docs 查文件、astryx component --list 列元件，連「全域裝還是專案裝」都有專門的說明。換句話說，它假設呼叫工具的可能不是人，是另一個 AI，所以說明書要寫到機器讀了也不會走歪。這個標準拿回來看我們自己的東西很有用：工具站的 builder 腳本、復核流程，如果哪天要交給另一個 AI 接手，現有的說明夠不夠它不問人就跑完？Astryx 的答案是——夠，才叫 ready。

我們怎麼用：昨天的三個偷法（配色收進 CSS 變數、共用片段做成可複製的範本、把工具站說明寫清楚）今天仍然有效，不重複。今天加一個：下次給 Hark 或 ChatGPT 交辦工具站改版時，先檢查交辦文件裡有沒有「AI 讀了會走歪」的地方——Astryx 的標準是，說明書要寫到另一個 AI 不問人也能跑完。真想試它：找個有 React 19 的小專案跑 npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex，用 CLI 列元件玩玩看；還在 Beta，別直接上生產環境。

HA-MCP：讓 Claude、ChatGPT 開口指揮你家——智慧家庭終於有了 AI 的嘴

homeassistant-ai / ha-mcp · MIT 協議 · Python · 87 個工具 · 需 Home Assistant 2026.8.0 以上

插畫：HA-MCP 在 Home Assistant 裡跑一個 MCP 伺服器，AI 助手連上它就能開關燈、調恆溫器、查設備狀態——不用再一個個點 App。

一句話人話

家裡裝了 Home Assistant 的人有福了：這個東西讓 Claude、ChatGPT 直接跟你家對話——「把燈調暗」「睡前關暖氣」一句話，AI 自己去按開關，不用你再打開 App 一個個點。

它到底是幹嘛的

一個給 Home Assistant 用的 MCP 伺服器，README 徽章標了 87 個工具。推薦裝法是裝進 Home Assistant 裡面跑：在 Home Assistant 2026.8–2026.10 從 HACS 搜尋 HA-MCP 下載，2026.11 以上直接在「設定 → Marketplace」搜尋安裝；裝好重啟，建一個管理員用的長期存取權杖（或專門開一個 HA-MCP 帳號），在「設定 → 裝置與服務」加入 HA-MCP Server，貼上權杖、選連線方式，就能拿到一條連線網址，貼進 Claude、ChatGPT 或任何 MCP 客戶端就好。不想裝整合的話也有 Docker（ghcr.io/homeassistant-ai/ha-mcp）和 uvx ha-mcp@latest 兩種跑法，另有 15 個以上客戶端的設定精靈幫你生設定檔。README 特別強調：遠端存取預設是關的，不開就不會註冊 webhook；也可以只留在區網內用，連線網址就是個秘密網址，別外洩。

它火在哪

一是剛好踩在兩個風口的交點上：MCP 已經是 AI 助手接外部工具的通用語言，Home Assistant 又是自架智慧家庭的事實標準，兩邊的使用者一疊加，數字自然好看——一天 +792 星，增幅 13.58%。二是它解決的是真痛點：以前要 AI 幫你管家裡，得自己寫一堆自動化腳本；現在 AI 直接讀得到設備狀態、按得到開關，門檻從「會寫 YAML」降到「會講話」。三是官方味很重：整合進了 Home Assistant 2026.11 的 Marketplace 預設目錄，等於半個官方背書，裝起來沒有「第三方野路子」的疑慮。

值得學什麼

「工具太多時，要給 AI 一個找工具的方法」。87 個工具一次全塞給模型，上下文就被吃掉大半，README 裡專門有一節講 Tool Discovery：支援搜尋式探索、每個網址一份工具目錄、唯讀連線，小模型或本地模型也能用。這個思路可以直接搬到我們自己的流程上——工具站的 builder 腳本、復核用的檢查清單越來越多時，與其一次全攤開，不如學它做「先搜尋、再取用」。第二，安裝路徑分層寫得清楚：整合版、App 版、Docker、uvx、stdio 五種跑法各有定位，還明說 stdio 只適合試玩、正式用走 HTTP——一份 README 讓新手不迷路、老手不踩坑，這個寫法值得學。

我們怎麼用：家裡如果有跑 Home Assistant（樹莓派或備用小主機就能跑），這是現成的 AI 遙控器：裝整合、貼網址進 Claude，睡前一句話關全屋燈，比寫自動化腳本快得多。就算家裡沒裝，README 裡的「搜尋式工具探索」也值得偷進我們的復核流程——檢查清單一多，就別一次全餵給 AI，改成先搜尋再取用。安全提醒照 README 的說法：連線網址是秘密網址，別貼到公開地方；遠端存取用不到就保持關閉，區網內用就夠了。

billion-context：AI 寫程式寫到一半失憶？這個壓縮器讓一個會話活一個月

ranxianglei / billion-context · 授權：README 寫 MIT＋一項署名條款（GitHub 頁面未標示明確授權） · TypeScript · 支援 pi / Claude / Codex / Gemini 等二十多種客戶端

插畫：長會話一路寫下去，舊對話被折成高保真摘要塞回去——模型自己決定什麼時候壓、壓什麼，壓完還能翻回來。

一句話人話

用 AI 寫程式寫久了都會遇到同一件事：會話越長、腦子越滿，最後不是失憶就是爆掉。這個外掛卡在 AI 跟模型中間，邊寫邊把舊對話壓成摘要，號稱一個會話能活一個月、token 省五倍，100K 上下文就夠用。

它到底是幹嘛的

一個上下文壓縮外掛，坐在任何 coding agent 跟模型 API 之間，重寫 Anthropic / OpenAI 的資料流，用 acp-kernel 做壓縮。做法不是硬砍對話，而是由模型自己決定什麼時候、把哪一段壓成高保真摘要——壓縮是漸進式、可逆、而且對前綴快取友善的，摘要寫在小範圍裡，需要時可以解壓回來。壓縮器會往對話裡注入四個上下文管理工具，模型在上下文變長時自己呼叫：compress 把一段訊息折成詳細摘要、decompress 需要精確細節時還原、search_context 在壓縮過的摘要裡關鍵字搜尋、acp_status 看上下文用量跟哪些範圍還能壓。支援的客戶端很多，pi、Claude、Codex、Gemini、Qwen、Kimi、Trae 等二十多種，裝法分兩種：原生外掛（bili plugin install pi 這類）或啟動器（bili pi、bili claude 這類）。先裝本體：npm install -g billion-context --prefix=~/.local。README 自稱的數字：token 省 5 倍、健康會話的前綴快取命中率 95–97%、壓縮本身成本不超過 2%；還附了一篇開源的論文跟一份 1,500 項的第三方交叉評測，數據來源都寫在 README 裡，有興趣自己點進去看。

它火在哪

一是「回歸」本身就是故事：11 月 8 日那期它一天增幅 9.87%，只差 0.13 個百分點沒進主榜（當時門檻還是 10%）；門檻放寬到 5% 後，它今天以 6.32% 正式進榜——等於是被新門檻撈回來的第一個名字。二是痛點夠普世：現在人人都在跟 AI 結對寫程式，上下文爆掉是每個人的日常，它賣的不是新功能，是「不用換會話」的自由。三是野心寫在名字裡：billion-context，十億級 token 的單一會話，README 裡的縱向研究寫了 4.5 個月、174,327 次模型呼叫、累計 18.76B token——數字擺得很大，信不信由你，但至少它敢把論文跟評測都開源出來讓人驗。

值得學什麼

「讓模型自己決定壓什麼」這個設計值得記下來。大多數上下文管理是硬規則：超過多少 token 就砍頭、或固定每幾輪摘要一次。billion-context 反過來，把 compress / decompress / search_context 做成工具交給模型自己呼叫，壓縮變成模型工作流程的一部分，而不是外掛在旁邊的剪刀。這個思路搬到我們自己的流程上很有啟發：復核用的檢查清單、工具站的每日抓取，與其寫死「跑滿幾步就停」，不如讓執行者自己判斷「這段可以折起來了」。第二，它對「可逆」的堅持：摘要可以解壓回來，壓過的範圍還能關鍵字搜尋——壓縮不是丟掉，是換個地方放著，這個取捨比「砍掉重練」聰明得多。

我們怎麼用：最直接的場景就是我們自己的長會話：工具站回填、CANSLIM 資料盤點這種動輒幾小時的活，會話一長就得開新的、上下文全丟——裝一個 npm install -g billion-context --prefix=~/.local，下次長任務試試 bili pi 或對應的啟動器，看它能不能讓一個會話撐完整場。但先潑兩盆冷水：第一，它是卡在中間重寫 API 資料流的代理，正式用之前先讀一下它怎麼處理你的 API key，別拿主力 key 直接上；第二，README 裡的 5 倍、95% 命中率都是它自己報的數，論文跟評測雖然開源，但我們沒親自驗過——先在小任務上試，別一上來就押長任務。
